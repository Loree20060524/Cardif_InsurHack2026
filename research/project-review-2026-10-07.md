# 法遵前哨站 專案檢視與功能建議

檢視日期：2026-10-07。範圍為目前資料夾的程式、文件、本機資料快取與既有測試；未修改業務程式。Git 工作目錄連結失效，因此未以提交差異作為檢視依據。瀏覽器未能連上本機 8082 服務，畫面建議依 HTML、CSS、JavaScript 與測試判斷，未完成瀏覽器實際操作驗證；未驗證真實 Ollama 推論品質或重新抓取官方資料。

## 整體判斷

目前具備官方來源整合、資訊分類與篩選、歷史資料載入、規則備援、按需 AI 分析，以及使用者自行選取資訊的管理摘要。Python 已分成 domain、application、infrastructure、web；前端也已按功能拆檔，有可延伸的基礎。

最有價值的下一步是讓使用者清楚看見「哪些內容真的改了」及「分析依據在哪裡」，再改善個人關注與報告輸出。建議維持目前公開監理情報的定位。

本機快取包含 366 筆資訊、5 個來源；法規版本庫包含 258 部法規，其中只有 4 部具有多個保存版本。這些數字反映本機已保存資料，不能當作官方資料的完整涵蓋率。

## 優先改善

### 1. 讓重新分析真正重新呼叫模型

`assets/js/ai-analysis.js` 的 `force` 只影響部分前端判斷，送出的請求仍是 `/api/analyze?id=...`；`regintel/web.py` 沒有把強制重新分析參數傳到應用層，`regintel/application/event_analysis.py` 仍會直接回傳既有 AI 快取。

目前詳細頁的按鈕會先清除 `aiRequested`，能送出請求，但不能繞過後端快取。另外，直接連續呼叫 `ensureAIAnalysis(event)`、`ensureAIAnalysis(event, true)`，第二次仍會被成功後保留的 `aiRequested` 擋下；既有前端測試只涵蓋預先帶有完成結果的事件，沒有涵蓋這個連續操作。

建議建立明確的重新分析請求，讓前後端都處理 `force`；將「請求正在進行」與「已有結果」分開管理，並以完整 API 測試確認重跑時確實再次呼叫模型。

### 2. 補強測試隔離與實際整合測試

- JavaScript 9 項測試中 8 項通過；`tests/test_dashboard_rendering.js` 的清單測試沒有載入 `assets/js/pagination.js`，因此出現 `pageWindow is not defined`。正式 HTML 有載入此檔案，這不是已證實的正式頁面錯誤。
- Python 在沒有既有快取的隔離副本中整批執行，27 項中 26 項通過。剩餘的快取失效測試改用獨立歷史快取後通過，顯示整批測試會受到前一項測試保存的歷史資料影響。
- 更新流程測試只替換了 `refresh` 模組的部分讀寫方法，沒有隔離 `event_history` 的儲存路徑，可能讀取或寫入正式執行資料。第一輪檢查產生的兩筆測試歷史資料已移除，保留既有資料並還原原始快取大小。

建議每項涉及資料儲存的測試使用獨立暫存目錄，並補上「分析完成後重跑」、「來源部分失敗」、「分析中更新資訊」等整合情境。

### 3. 縮小長時間鎖定範圍，改善等待體驗

`refresh_data()` 在 `_cache_lock` 內依序處理來源與網路請求；`analyze_event_with_ai()` 在共享 AI 快取鎖內呼叫 Ollama。模型逾時設定是 180 秒，遇到慢來源或慢推論時，其他需要同一把鎖的請求可能等待。

建議先回傳可用資料快照，由背景工作更新來源；AI 工作採有限併發佇列，僅在讀寫快取時鎖定，並用事件識別與內容版本避免重複推論。畫面呈現等待、讀取來源、推論、完成等實際狀態。此項是程式結構分析，未做效能壓力測試。

### 4. 整理介面樣式與版本標示

`index.html` 仍有約千行內嵌樣式覆蓋既有 CSS，並另有側欄控制器；`assets/js/app.js` 也保存側欄控制邏輯。HTML 樣式註記為 v11.1，README 與後端版本為 10.19。

建議將目前正式使用的樣式收回對應 CSS 檔，集中設計變數，合併側欄控制邏輯，統一版本標示。先保留原生 JavaScript 架構即可。

### 5. 修復版本管理與改善錯誤可觀測性

`.git` 指向已不存在或不可用的 `RegIntel_v10_5_ActionEngine/.git/worktrees/RegIntel_5aad25d_fix`，目前 `git status` 與 `git log` 都失敗。應先找回原始儲存庫與工作目錄關係，再進行修改與提交。

JSON 儲存與部分內容讀取錯誤目前被忽略。建議保留來源錯誤與寫入失敗的診斷紀錄，區分「沒有資料」、「讀取失敗」與「檔案損毀」。目前資料量不大；SQLite 可在歷史資料、個人設定與報告保存需求增加時導入，不必立即全面改寫。

## 建議新增功能

| 優先順序 | 功能 | 最小可用版本與價值 |
|---|---|---|
| 1 | 法規修正前後對照 | 以已保存的兩個官方版本逐條標示新增、刪除與修改，附版本日期和來源；讓使用者直接看懂異動。只有單一版本時，明示缺少比較基準，不推測舊條文。 |
| 2 | 分析證據檢視 | 每項監理重點、風險理由、部門影響都可展開對應原文與條號／附件頁碼；區分原文事實、系統判斷與待確認事項，顯示分析時間與來源讀取範圍。 |
| 3 | 部門與主題關注清單 | 儲存常用篩選、收藏與已讀狀態，依使用者設定標示新增的重要資訊；先做站內個人化，後續再延伸定期摘要。 |
| 4 | 管理摘要匯出與保存 | 匯出 PDF／Excel 或列印版，保留選取資訊、生成時間、來源與分析版本；讓摘要可用於主管會議，並可回看過去產出的報告。 |
| 5 | 監理日期時間軸 | 分開呈現公告日、生效日、意見徵詢截止日等官方明示日期；支援日曆匯出。來源未載明時保留待確認，不以抓取時間代替。 |
| 6 | 裁罰案例與關聯資訊 | 依違規主題、流程缺失與來源整理案例，串接相關法規及公告；金額與條文只收錄可核對的內容。 |

目前已有部分附件節錄提醒與不足內容的規則備援。證據檢視應延伸這些機制：顯示哪些附件讀取成功、哪些段落實際送入模型，以及哪些判斷還缺乏直接證據。管理摘要目前每筆來源提供最多 900 字摘錄，長公告可進一步依主題與條文分段擷取，減少只取開頭造成的資訊遺漏。

## 建議實作順序

1. 修復 Git 工作目錄、重新分析的快取行為及測試隔離。
2. 完成法規版本對照與分析證據檢視，作為核心展示功能。
3. 加入關注清單與摘要匯出，提升日常使用價值。
4. 依使用量改善背景更新、工作佇列與持久化儲存。

若近期只做一個新功能，優先選法規修正前後對照；若目的是讓分析結果更容易被採用，優先選分析證據檢視。
